### 一键安装与后端版本校验（仍不行时的改进）
- **变更类型**：部署、接口
- **主要内容**：（1）**/api/health** 响应增加 **preset_version: "3.0"**，便于用 `curl http://服务器:8080/api/health` 确认当前后端是否为预设 v3.0。（2）**install.sh** 当安装目录非空且无 .git 时，改为**克隆到子目录 nofx-src/** 并复制现有 .env、keys、data 到 nofx-src，再在该目录内构建并启动，实现**原地升级**，无需清空目录或换路径。（3）脚本内数据库路径由 data/nofx.db 改为 **data/data.db** 与后端一致。
- **涉及**：`api/server.go`、`install.sh`、`docs/更新记录.md`

### 一键安装脚本改为从源码构建（解决云服务器一键生成仍为 v2.0）
- **变更类型**：部署
- **主要内容**：**install.sh** 不再拉取预构建镜像（docker-compose.prod.yml + pull），改为 **克隆 dev 仓库并本地构建**：clone_or_pull_repo（无 .git 时 git clone dev 到当前目录，有 .git 时 git pull）、build_images（docker compose build --no-cache）。这样执行 `curl -fsSL .../install.sh | bash` 后云服务器会使用 GitHub dev 最新代码，一键生成策略为**预设 v3.0**（2.5%/6%/10% 等）。首次安装需保证目标目录为空；已安装过的目录（已有 .git）再次执行脚本会 pull 并重新构建。
- **涉及**：`install.sh`、`docs/更新记录.md`

### 云服务器「一键生成」仍为旧版说明与验证
- **变更类型**：说明、接口、前端
- **原因**：一键生成（紫色星星）的配置由**当前运行的后端进程**实时调用 `GetOptimizedStrategyConfig` 返回。若云服务器只做了 `git pull` 而未**重新构建镜像并重启容器**，进程仍是旧代码，返回的即为旧预设。
- **处理**：在云服务器上执行**重新构建并重启**后再使用一键生成，例如：
  - Docker：`docker compose pull`（若用镜像仓库）或 `docker compose build --no-cache nofx nofx-frontend`，然后 `docker compose up -d`
  - 或重新构建后端镜像后 `docker compose up -d --force-recreate`
- **本次修改**：创建预设策略 API 响应增加 `preset_version: "3.0"`；前端成功提示改为「预设策略 v3.0 已创建」（若接口返回其他版本则显示该版本），便于确认当前后端已是新预设。
- **涉及**：`api/strategy.go`、`web/src/pages/StrategyStudioPage.tsx`、`docs/更新记录.md`

## 重装/重新部署后为何「新建交易员」仍有历史仓位？

- **原因**：历史仓位是按 **交易员 ID** 存在数据库里的；数据库文件在 **数据目录**（默认 `./data`，Docker 下常挂载为 `./data:/app/data`）。若重装系统或重新部署时**没有清空或替换该数据目录**，则：
  - 数据库（如 `data/data.db`）仍是旧数据；
  - 其中的**交易员**和**仓位/统计**都还在；
  - 您看到的「一个交易员」很可能是**重装前就存在**的那位，而不是真正新建的；或您新建了一位，但当前选中的仍是列表里另一位（旧）交易员，所以看到的是旧的历史（如 7 笔）。
- **结论**：出现「新建交易员却有历史仓位」时，说明**当前使用的数据库是旧的**，未做「全新库」的初始化。
- **若需要从零开始**：（1）停服务后删除或清空数据目录（如 `./data`，注意备份），再启动，会生成新库，所有交易员与仓位需重新创建；或（2）保留数据但在界面中**确认当前选中的是新建的那位交易员**（列表按创建时间倒序，新建的会排在最前），新建的那位历史应为 0。
