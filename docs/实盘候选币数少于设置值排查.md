# 实盘「候选币数」少于策略设置值排查说明

## 策略里的两个概念

1. **写入 Prompt 的候选币数**（`max_coins_in_prompt`，界面「候选币数」）  
   - 含义：**最多**往 AI 思维链里放多少个候选币（不含当前持仓）。  
   - 例如设为 4：表示「最多 4 个候选币」参与分析，不是「一定 4 个」。

2. **候选币来源**（币种来源 / 信号源）  
   - 由策略的「币种来源」决定：静态列表、AI500、OI Top/Low 或混合。  
   - 实际参与思维链的数量 = **min(本周期拿到的候选列表长度, max_coins_in_prompt)**，再减去「拉取失败」和「OI 过滤」被跳过的数量。

因此：**策略里设 4，只分析 1～2 个币，是正常可能出现的**，常见原因见下。

---

## 常见原因

### 1. 候选列表本身就只有 1～2 个

- **静态列表**：若「静态币种」只配了 1～2 个，那每周期只会拿到 1～2 个候选。  
  → 在策略里增加静态币种，或改用 AI500 / OI 等来源以获取更多候选。
- **AI500 / OI Top(Low)**：  
  - 云上**信号源 API 不可达或失败**（超时、403、网络不通）时，`GetCandidateCoins()` 会报错，实盘会退化为**空列表**（0 个候选），或由混合模式里的静态兜底，若静态也少则只有 1～2 个。  
  - API 正常但返回列表很短（例如当前只推荐 1～2 个币），也会只分析 1～2 个。  
  → 在云服务器上确认能访问信号源（如 `https://nofxos.ai` 或自建），看日志是否有 `Failed to get candidate coins` 或 `Strategy engine fetched candidate coins: 0`。
- **混合模式**：同时开 AI500 + OI + 静态时，列表是合并去重后的结果；若 API 失败或返回少，最终列表仍可能只有 1～2 个。

### 2. 拉取行情失败（fetch_fail）

- 每个候选币都会用 `market.GetWithTimeframes(...)` 拉 K 线/指标；**任意一个币拉取失败**，该币本周期就不会进 Prompt。  
- 云上常见：交易所 API 限频、网络超时、防火墙/代理拦截、或该交易对在云环境不可用。  
- 日志会看到：`Failed to fetch market data for SYMBOL: ...`，以及汇总里的 **skipped: fetch_fail=N**（N>0）。

### 3. OI 过滤（OI_low）

- 代码里对**非 XYZ 链上资产**会做流动性过滤：`OI 价值 < 1500 万美元` 的币会被跳过，不写入 Prompt。  
- 若多个候选币 OI 偏低，最终进 Prompt 的就会少于 4。  
- 日志会看到：`SYMBOL OI value too low (...M USD < 15.0), skipping coin`，以及 **skipped: OI_low=N**（N>0）。

---

## 如何用日志确认

实盘/模拟每周期会打一条汇总日志，例如：

```text
📊 Market data: 1 positions + 2 candidate coins in prompt (max candidates=4; total candidates=3; skipped: fetch_fail=0, OI_low=0)
```

含义：

- **max candidates=4**：策略里「写入 Prompt 的候选币数」= 4。  
- **total candidates=3**：本周期策略引擎**实际拿到的候选列表长度**为 3（例如 AI500 只返回 3 个，或静态只有 3 个）。  
- **2 candidate coins in prompt**：扣除持仓、拉取失败、OI 过滤后，**真正写入 Prompt 的候选数**为 2。  
- **skipped: fetch_fail=0, OI_low=0**：本周期没有因拉取失败或 OI 低被跳过。

若你看到的是「只分析 1～2 个币」：

- 先看 **total candidates**：  
  - 若 total=1 或 2 → 问题在**候选来源**（静态太少、或 AI500/OI 在云上失败/返回少）。  
  - 若 total≥4 但 **candidate coins in prompt** 只有 1～2 → 多半是 **fetch_fail** 或 **OI_low** 导致被跳过，再结合上面的 `Failed to fetch market data` / `OI value too low` 日志排查。

另可看前一行：

```text
📋 [交易员名] Strategy engine fetched candidate coins: N
```

这里的 **N** 就是本周期拿到的候选列表长度；若 N 经常是 0 或 1～2，说明信号源在云上返回不足或失败。

---

## 云上建议

1. **确认信号源在云上可用**  
   若用了 AI500 / OI：在云服务器上测试能否访问对应 API（如 nofxos 的 BaseURL），并确认策略里配置的 API Key 在云环境有效。若不可用，可改为「静态列表」或混合模式并多配几个静态币种，保证至少有一定数量的候选。

2. **看日志里的 total / skipped**  
   按上面说明区分：是「候选列表就少」还是「列表够但被 fetch/OI 筛掉」。  
   - 列表少 → 修信号源或加静态。  
   - fetch_fail 多 → 查云上网络、交易所限频、超时。  
   - OI_low 多 → 正常过滤行为，或考虑放宽/调整策略（需改代码或配置）。

3. **静态兜底**  
   在「币种来源」里配置若干**静态币种**（如 BTC、ETH 等），即使 AI500/OI 在云上失败，仍会有固定 1～2 个或更多候选，避免每周期 0 候选。

4. **写入 Prompt 的候选币数**  
   `max_coins_in_prompt=4` 只表示「最多 4 个」；实际多少由上面三者共同决定：候选列表长度、拉取是否成功、OI 是否过滤。要「尽量接近 4」，需要先保证「候选列表≥4」且尽量少被 fetch/OI 跳过。

---

## 小结

- **「写入 Prompt 的候选币数: 4」** = 上限 4，不是保证每周期都 4 个。  
- 实盘只分析 1～2 个币，通常是：**候选列表只有 1～2 个**（尤其云上信号源失败/返回少）、或**拉取失败 / OI 过滤**导致多个被跳过。  
- 通过日志中的 **total candidates** 与 **skipped: fetch_fail / OI_low** 即可判断是哪一类，再按上文逐项排查即可。
