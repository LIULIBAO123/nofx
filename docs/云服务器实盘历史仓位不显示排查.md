# 云服务器实盘「历史仓位」不显示排查说明

## 现象

云服务器实盘交易员仪表盘中，「历史仓位」区块报错、一直加载，或**没有平仓历史记录**（列表为空、确认已在交易所平过仓）。

---

## 一、平仓历史记录「没有」——为什么库里没有已平仓记录？

平仓历史来自数据库里 `trader_positions` 表中 **status = 'CLOSED'** 的记录。这些记录**不是**在您点平仓的瞬间就写进库的，而是由后台 **OrderSync** 从交易所拉取成交后，再写入/更新到本地库的。

### 1. 订单/仓位同步（OrderSync）只在「交易员运行中」执行

- Binance / Bybit / OKX / Bitget 等实盘：**只有在该交易员处于「运行中」时**，才会每 30 秒跑一次 OrderSync，从交易所拉成交并把对应仓位标为已平仓（CLOSED）。
- 若平仓后**从未启动过该交易员**，或平仓后**很快就把交易员停了**，OrderSync 可能一次都没跑到、或没跑到「包含这笔平仓」的那次，本地就**不会**产生这条平仓历史记录。

**建议**：平仓后至少让该交易员**再保持运行一段时间**（例如 1～2 分钟），或之后**再启动一次该交易员**，让 OrderSync 有机会拉取到这笔平仓成交并写入历史。

### 2. 云端 data 是新的或未持久化

- 若云服务器是**新部署**或**新挂了一个空 data 目录**，库里本来就没有任何历史，自然没有平仓记录。
- 若 data 目录**没有挂载**或重启后丢失，每次重启都会用新库，之前的平仓记录也会消失。

**建议**：确认云上部署时 `./data`（或当前使用的 DB 目录）已挂载并持久化，且没有在每次重启时被清空。

### 3. OrderSync 拉取失败

- 网络、交易所 API 限频、鉴权失败等，会导致当次 OrderSync 失败，该周期内的平仓成交可能没被写库。
- 可在云服务器上查看后端日志（如 `docker compose logs nofx --tail=200`），搜索 OrderSync、SyncOrders、Failed、error 等，看是否有报错。

### 4. Binance 单向持仓（positionSide=BOTH）被误判为开仓（已修复）

- **原因**：Binance 在**单向持仓模式**下成交返回 `positionSide="BOTH"`。旧逻辑在 `positionSide` 为 BOTH 时走默认分支，**没有根据 realizedPnL 判断平仓**，把平仓成交当成开仓处理，只写了订单、没有把仓位标为 CLOSED，所以「有平仓订单、没有平仓记录」。
- **修复**：在 `determineOrderAction` 中对 `positionSide == "BOTH"` 单独分支，用 `realizedPnL != 0` 判定为平仓并返回 `close_long`/`close_short`，OrderSync 会正确写入/更新 CLOSED 仓位记录。
- **生效**：需部署含该修复的后端；修复后新同步的平仓会正常出现历史记录，**之前已误同步为开仓的成交不会自动改回**，可依赖后续平仓或重新部署后从交易所重新拉取（视同步窗口而定）。

### 小结（平仓历史「没有」时）

| 情况 | 建议 |
|------|------|
| 平仓后交易员一直没在运行 | 启动该交易员，让 OrderSync 跑几轮，或至少运行 1～2 分钟再停 |
| 云端 data 新库/未挂载 | 确认 data 目录挂载且持久化，避免重启丢库 |
| 怀疑同步失败 | 看后端日志里 OrderSync 是否有报错 |
| Binance 单向持仓（BOTH）| 已修复：BOTH 时按 realizedPnL 判平仓；部署后新同步的平仓会有记录 |

## 二、其他可能原因（有记录但不显示 / 报错）

### 1. 接口需登录，未带 Token 或 Token 失效

- **接口**：`GET /api/positions/history?trader_id=xxx` 为**需认证**路由，与净值曲线一致。
- **表现**：未登录或 Token 过期时返回 401，前端会提示「获取历史仓位失败」；更新后**错误详情会显示后端返回原因**（如 Invalid trader ID）。
- **排查**：先确认已登录再打开该交易员仪表盘；若仍报错，看错误框中的**具体文案**（如 Invalid trader ID）。

### 2. trader_id 未传或不属于当前用户

- **逻辑**：未传 `trader_id` 时，后端会使用「当前用户第一个交易员」；若该交易员 ID 与当前页不一致，或用户无交易员，会 400/404。
- **排查**：浏览器开发者工具 → Network，找到 `positions/history?trader_id=...`，确认请求带上了当前交易员的 `trader_id`，且响应状态码与 body 中的 `error`/`message`。

### 3. 交易员未加载或加载失败（404）

- **逻辑**：历史仓位依赖「当前交易员」已从 DB 加载到内存；若该交易员配置异常（如交易所/策略缺失），可能加载失败，接口返回 404。
- **排查**：看接口是否返回 404；若是，查看云服务器后端日志（如 `docker compose logs nofx --tail=100`），是否有该交易员加载失败或 GetTrader 相关错误。

### 4. 数据库里没有该交易员的 CLOSED 仓位（空列表）

- **逻辑**：历史仓位来自表 `trader_positions` 中 `trader_id = 当前交易员` 且 `status = 'CLOSED'` 的记录。新部署、新数据目录、或平仓从未被正确写入/同步为 CLOSED 时，列表会为空。
- **表现**：接口返回 200，`positions: []`，前端显示「暂无历史仓位」。
- **排查**：
  - 确认云服务器上挂载的 `./data`（或当前使用的 DB 路径）是否为预期库（是否有其他环境在用别的 data 目录）。
  - 若为全新部署且未做过平仓，空列表属正常；若有平仓但无记录，需排查 OrderSync/平仓逻辑是否把仓位标为 CLOSED 并写入 DB。

### 5. 数据目录/库不一致（多机或重装）

- **说明**：若云服务器重装或换机后使用了**新的**数据目录，则新库中不会有旧机器的历史仓位；反之若沿用旧 data，则会有旧数据。
- **排查**：确认当前容器/进程使用的 DB 路径（如 `data/data.db`）与预期一致；必要时对比本地与云上 `trader_positions` 表中该 `trader_id` 的 CLOSED 记录数量。

## 建议排查顺序

- **若是「平仓历史记录没有」**：先看**一**：该交易员平仓后是否**保持运行**过（让 OrderSync 拉取）、云端 **data 是否挂载持久化**、后端日志里 OrderSync 是否报错。
- **若是报错「获取历史仓位失败」**：看前端具体错误文案、Network 里 `positions/history` 的请求是否带 Token、响应状态码与 body。
- **通用**：后端日志 `docker compose logs nofx --tail=100`，确认有无 400/404/500 或 OrderSync 相关错误。

## 小结

- **平仓历史记录没有**：实盘已平仓记录依赖 **OrderSync** 从交易所拉取；OrderSync 只在**交易员运行中**执行。平仓后请让该交易员至少再运行 1～2 分钟（或之后再启动一次），并确保云端 **data 目录已挂载且持久化**。
- 历史仓位接口**需登录**；若接口报错，前端会展示后端返回的具体原因，便于继续排查。
