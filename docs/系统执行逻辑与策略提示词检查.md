# 系统执行逻辑与策略/提示词检查报告

本文档梳理新功能（多层过滤、方向池、雷达、第三层校验、实时价格）下的**整体执行逻辑**与**代码结构**，并说明**提示词**与**策略配置**已做或建议的变更。

---

## 一、整体执行逻辑（数据流）

```
auto_trader.runCycle()
  │
  ├─ 构建 ctx：CandidateCoins = GetCandidateCoins()（币种源：static/ai500/oi_top/oi_low/mixed）
  ├─ 拉取 OIRankingData、NetFlowRankingData、PriceRankingData（供 pipeline 第一层使用）
  ├─ 拉取雷达配置（GetRadarConfigBytes）→ PipelineOptions{ AllowLong, AllowShort }
  │
  └─ GetFullDecisionWithStrategy(ctx, ..., traderID, pipelineOpts)
        │
        ├─ 1. fetchMarketDataWithStrategy(ctx)
        │       · MarketDataMap = 持仓 + 最多 maxCandidateCoinsForPrompt 个候选的 K 线/指标
        │       · 候选来源为当前 ctx.CandidateCoins（此时仍为币种源完整列表）
        │
        ├─ 2. [若 strategy_mode == multilayer_filter] RunPipeline(ctx, config, traderID, opts)
        │       · 仅对「已在 MarketDataMap 中的候选」做过滤（无行情数据的候选不进入池）
        │       · Layer1 逐项检查 → Layer2 因子/可靠度/信心 → 方向池划分 → 按 AllowLong/AllowShort 过滤 toSubmit
        │       · ctx.CandidateCoins 被替换为 state.ToSubmitSymbols（仅「待提交」）
        │       · 状态写入 SetPipelineState(traderID)，供多空雷达 API 读取
        │
        ├─ 3. BuildSystemPrompt(equity, variant)  // 与是否多层过滤无关，沿用现有 Schema + 风控 + 模式
        ├─ 4. BuildUserPrompt(ctx)               // 仅遍历 ctx.CandidateCoins → 此时已是「待提交」列表
        │       · 启用多层过滤时增加一句说明：候选已通过多层过滤，仅可对下列标的建议开仓
        │       · 候选标题使用 len(ctx.CandidateCoins)
        │
        ├─ 5. callAIWithCaching → 解析 JSON 决策
        │
        └─ 返回 FullDecision
  │
  └─ 对每条决策 executeDecisionWithRecord(decision)
        │
        ├─ open_long / open_short 时：
        │     · 先执行既有校验（置信度、最大持仓、盈亏比等）
        │     · 若策略启用多层过滤且 Layer3.MaxSignalAgeMinutes > 0：
        │         ValidateLayer3(symbol, "long"|"short", traderID, maxMin)
        │         → 校验 pipeline 状态未超时且 symbol 在 ToSubmitSymbols 中，否则拒绝开单
        │     · 通过后 OpenLong / OpenShort
        │
        └─ 持仓监控：checkDynamicStopLossTakeProfit（每次调用时 GetPositions 拉取最新 mark 价，满足「实时价格」）
```

要点：

- **候选收敛时机**：在拉取行情之后、建 UserPrompt 之前，由 RunPipeline 把 `ctx.CandidateCoins` 收束为「待提交」列表；AI 看到的候选 = 已过多层过滤。
- **Pipeline 入口**：只对 `ctx.MarketDataMap` 中已有数据的候选做 Layer1/Layer2/方向池，避免无数据标的被误判为通过。
- **开单前**：仅对 open_long/open_short 做 Layer3（信号年龄 + 是否在待提交列表），与截图设计一致。

## 二、策略配置是否需要改

| 项目 | 是否需要改 | 说明 |
|------|------------|------|
| **新策略（默认/优化预设）** | 已改 | `GetDefaultStrategyConfig` / `GetOptimizedStrategyConfig` 已设置 `StrategyMode: "multilayer_filter"` 与完整 `MultilayerFilter`（Layer1/2/3）。新创建的策略默认即启用多层过滤。 |
| **已有策略（DB 中旧配置）** | 可选 | 未包含 `strategy_mode` / `multilayer_filter` 时按原逻辑：不跑 pipeline，候选=币种源列表，行为与之前一致。若希望老策略也走多层过滤，需在策略编辑里勾选或写入 `strategy_mode`、`multilayer_filter`。 |
| **风控与实时价格** | 可选 | `RealtimePriceConfig` 已在 `RiskControlConfig` 中定义；若需「SL/TP 前强调使用最新价」，可配置 `realtime_price.enabled` 与 `fetch_before_sltp_check`。当前实现已在每次 SL/TP 检查时拉取持仓，语义已满足。 |
| **PromptSections** | 不必改 | 角色、频率、入场标准、决策过程等仍由 `PromptSectionsConfig` 控制；多层过滤仅影响「候选列表是谁」，不在系统提示里改这些段落。 |

结论：**策略层面**新功能已通过默认/优化预设接入；旧策略保持兼容，按需再开多层过滤即可。

## 三、提示词是否需要改（已做变更）

| 位置 | 是否改 | 变更说明 |
|------|--------|----------|
| **System Prompt** | 未改 | Schema、风控、模式、输出格式等与是否多层过滤无关，保持不变。 |
| **User Prompt – 候选段** | 已改 | 1）启用 `multilayer_filter` 时，在「Candidate Coins」前增加一句说明（中/英）：候选已通过多层过滤，仅可对下列标的建议开仓。2）「Candidate Coins (N coins)」的 N 改为 `len(ctx.CandidateCoins)`，即当前给 AI 的候选数量（多层过滤下=待提交数量）。 |
| **决策流程 / 入场顺序** | 未改 | 仍为「先看持仓 → 再定方向与入场 → 扫候选」。候选本身已被 pipeline 收窄，无需在提示词里再写一层过滤规则。 |

这样 AI 明确知道：**下面列出的候选是系统已过滤后的名单，只对这些标的建议开仓**，与「AI 只分析、系统执行」的截图思路一致。

## 四、代码结构要点

| 模块 | 职责 | 与新功能的关系 |
|------|------|----------------|
| **kernel/engine.go** | 拉行情 → 调 RunPipeline（若启用）→ 替换 CandidateCoins → BuildSystemPrompt / BuildUserPrompt → 调 AI → 解析决策 | 串联 pipeline 与提示词；UserPrompt 中根据 StrategyMode 增加多层过滤说明与候选数量。 |
| **kernel/pipeline.go** | 仅对「有 MarketDataMap 的候选」做 Layer1/Layer2/方向池/方向过滤 → ToSubmitSymbols；SetPipelineState 供雷达 API 使用；ValidateLayer3 供开单前校验。 | 入口处限制为有行情数据的候选，避免无数据标的进入待提交。 |
| **store/trader.go** | 雷达配置持久化（GetRadarConfigBytes / PutRadarConfigBytes）、radar_configs 表。 | 多空雷达页与 auto_trader 共用同一配置。 |
| **api/radar.go** | 多空雷达 GET/PUT 使用 store 读写；order-flow、direction-pool 从 kernel.GetPipelineState 取数。 | 与 pipeline 状态一致。 |
| **trader/auto_trader.go** | 跑周期时读雷达配置并传 PipelineOptions；执行 open 前调用 ValidateLayer3；SL/TP 检查时依赖每次 GetPositions 的最新价。 | 雷达配置与执行链路、第三层、实时价格均在此接入。 |

## 五、小结与建议

- **执行逻辑**：币种源 → 拉行情（含 OI/流向/涨跌榜）→ 仅对有行情的候选跑 pipeline → 替换候选为待提交 → 建提示词（并注明「已过多层过滤」）→ AI 决策 → 开单前 Layer3 校验 → 执行。逻辑闭环完整。
- **策略**：新策略默认启用多层过滤；旧策略不改则保持原样；提示词中无需再写「如何过滤」的规则。
- **提示词**：仅 UserPrompt 候选段做了两处小改（多层过滤说明 + 候选数量），System Prompt 与其余段落无需改。
- **建议**：若希望进一步强化「只对列表开仓」的约束，可在 System 的「Hard Constraints」或「Decision Process」中加一句：「Only suggest open_long/open_short for symbols listed in Candidate Coins.」当前通过「候选列表=待提交」+ 一句说明已能传达同一含义。
