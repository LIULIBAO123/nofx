# 新功能前后端对齐与可运行性分析

本文档对照**多空雷达、挂单流程信息、方向池**等新功能的**前端与后端**接口、类型与数据流，并评估**是否能正常工作**。

---

## 一、接口与路径对齐

| 功能 | 后端路由 | 前端请求 | 鉴权 | 结论 |
|------|----------|----------|------|------|
| 多空雷达配置 GET | `GET /api/traders/:id/radar-config` (protected) | `GET /api/traders/${traderId}/radar-config` | 是（Bearer） | ✅ 一致 |
| 多空雷达配置 PUT | `PUT /api/traders/:id/radar-config` (protected) | `PUT /api/traders/${traderId}/radar-config` + body | 是 | ✅ 一致 |
| 挂单流程信息 | `GET /api/traders/:id/order-flow-info` (protected) | `GET /api/traders/${traderId}/order-flow-info` | 是 | ✅ 一致 |
| 方向池 | `GET /api/traders/:id/direction-pool` (protected) | `GET /api/traders/${traderId}/direction-pool` | 是 | ✅ 一致 |

- 后端路由挂在 `api.Group("/api")` 下的 `protected := api.Group("/", s.authMiddleware())`，需登录。
- 前端 `httpClient` 在请求拦截器里从 `localStorage.getItem('auth_token')` 取 token 并设置 `Authorization: Bearer ${token}`，与后端一致。
- 前端使用的 `selectedTraderId` 来自交易员列表的 `trader_id`，与后端 `:id` 一致。

## 三、数据流与“能否正常工作”

### 3.1 多空雷达配置（radar-config）

- **GET**：后端从 `store.Trader().GetRadarConfigBytes(traderID)` 读；无则返回默认配置。前端用 SWR 拉取并 `radarConfig ?? defaultRadarConfig()`，展示与编辑均基于同一结构。
- **PUT**：前端 `updateRadarConfig(patch)` 合并后 `api.putRadarConfig(selectedTraderId, next)`，后端 `ShouldBindJSON(&req)` 后 `PutRadarConfigBytes(traderID, raw)` 持久化。
- **与 pipeline 的联动**：实盘/模拟在跑周期时会 `GetRadarConfigBytes(at.id)` 得到 `allow_long`/`allow_short`，构造 `PipelineOptions` 传给 `GetFullDecisionWithStrategy`，因此**雷达页勾选的“允许做多/做空”会真实影响 pipeline 的待提交列表**。

结论：前后端对齐，**能正常工作**；配置持久化且被执行逻辑使用。

### 3.2 挂单流程信息（order-flow-info）

- **数据来源**：`kernel.GetPipelineState(traderID)`；仅当该交易员在本周期内执行过 `GetFullDecisionWithStrategy` 且策略为 `multilayer_filter` 时，`RunPipeline` 会写入状态。
- **有状态时**：返回管线数量、流程阶段、第一层不达标统计、按币种不达标等，与前端展示的 `OrderFlowCard` 字段一一对应。
- **无状态时**：返回占位文案（如「暂无流程数据（请启动交易员并等待至少一个周期）」），前端照常渲染，不报错。

结论：前后端对齐；**能正常工作**。需注意：未启动交易员或未跑周期前会一直显示占位，属预期。

### 3.3 方向池（direction-pool）

- **数据来源**：同上，`kernel.GetPipelineState(traderID)` 的 `DirectionLong` / `DirectionShort`。
- **有状态时**：多/空列表与表格列（标的、强度、评分、市况、可靠度、时机、量价）一致。
- **无状态时**：返回 `{ long: [], short: [] }`，前端表格显示「当前无做多/做空候选」。

结论：前后端对齐，**能正常工作**。

### 3.4 前端对异常与空状态的处理

- **401**：httpClient 统一处理并跳转登录，雷达相关请求不会单独漏掉。
- **404**（如 trader 不存在或无权限）：后端返回 `{"error": "trader not found or no access"}`，httpClient 会 toast 并 throw，SWR 进入 error 状态；页面用 `orderFlow && <OrderFlowCard ... />`、`directionPool?.long ?? []` 等避免未定义访问，不会白屏或崩溃。
- **无数据**：占位或空数组均有明确结构，前端已做判空与默认值。

## 四、已知差异与说明（非错误）

| 项目 | 说明 |
|------|------|
| **「临时放宽第一层16项」** | 仅前端 localStorage，不写回后端，也不参与 kernel pipeline 逻辑；设计如此，非遗漏。 |
| **「设置为默认值」** | 目前仅前端按钮，未与策略默认配置或后端策略接口联动；仅影响当前页展示的“默认值”感，不破坏接口。 |
| **雷达配置的 HeatScore、可靠度门 等** | 前端可编辑并持久化到 DB，但 **pipeline 过滤逻辑** 当前只使用 **allow_long / allow_short**；其余字段为预留或将来与策略/风控联动用，不影响当前“对齐”与“能正常工作”的结论。 |

---

## 五、结论汇总

| 维度 | 结论 |
|------|------|
| **前后端是否对齐** | ✅ 是。接口路径、鉴权方式、请求/响应 JSON 结构（含 snake_case）与前端类型定义一致；占位与空状态均有约定。 |
| **是否能正常工作** | ✅ 能。配置的读写与持久化、挂单流程信息与方向池的展示、以及“允许做多/做空”对 pipeline 的生效，链路完整；异常与无数据时前端不崩溃，行为可预期。 |
| **建议** | 若希望 HeatScore、可靠度门等真正参与过滤，需在 kernel pipeline 或策略层增加读取与使用逻辑；当前仅保证前后端数据与接口一致、且已接入的功能可正常使用。 |
