# 数据获取常见错误与处理

本文说明在「数据统计」页面中常见的 Coinglass 等外部数据调用失败原因及处理建议。

---

## 一、错误信息如何查看

- 在 **数据统计 → 三、最近调用详情** 表格中，「错误信息」列现已**完整展示**（不再截断）。
- 点击该列中的 **「复制」** 按钮可把完整错误内容复制到剪贴板，便于排查或反馈。

---

## 二、常见错误类型与原因

### 1. `rate limit exceed` / 限流

**现象**：多条 Coinglass 调用失败，错误信息包含 `rate limit exceed` 或类似限流提示。

**原因**：  
Coinglass（或 KeyStore 代理）对同一 API Key 有**每分钟请求次数**限制。当前系统在以下场景会集中调用大量 Coinglass 接口：

- **系统周期**：过滤机制、方向池等会拉取 OI、资金费率、多空比、强平、恐惧贪婪、BTC 占比、ETF 资金流、鲸鱼指数、CDRI/CGDI、强平热力图等。
- **主周期**：同上。
- **止盈止损调整**：每个持仓的 SL/TP 分析周期内也会拉取上述数据。

若周期较短或多交易员/多标的并行，总 QPS 容易触及 Coinglass 套餐限速（例如 PROFESSIONAL 约 1200 次/分钟，参见 `docs/Coinglass-API对接与PROFESSIONAL套餐分析.md`）。

**建议**：

1. **拉长周期**：适当增大系统周期、主周期、止盈止损分析周期，减少单位时间内的调用次数。
2. **减少并发**：同一时段内减少同时运行的交易员数量或标的数量。
3. **升级套餐**：若业务需要更高 QPS，可考虑升级 Coinglass 套餐或联系 Coinglass/KeyStore 提高限速。

**系统已实现的限速与错峰**（针对中转站如「每分钟 10 请求」）：

- **每分钟请求数限速**：Coinglass 客户端支持 `coinglass_rate_limit_per_min`（策略 → 指标），默认 10。所有经该客户端的请求会按间隔 `60/rateLimitPerMin` 秒排队（如 10/min 即每 6 秒最多 1 次），保证不超出中转站限制。
- **按机制错峰**：同一分钟内若多机制都会拉 Coinglass，会先按机制延迟再发首请求，避免同时打满限速：
  - **系统周期**：不额外等待；
  - **主周期**：首请求前等待 20 秒；
  - **止盈止损调整**：首请求前等待 40 秒。
- 配置方式：策略配置中 `indicators.coinglass_rate_limit_per_min` 设为实际中转站上限（如 10），0 表示使用默认 10。

**数据完整性**：虽然请求在时间上错开（限速 + 机制错峰），但每个流程内 **FillCoinglassData / FillCoinglassDataForSLTP 为同步**，只有在本流程全部 Coinglass 请求执行完毕（含限速等待）后才返回。调用方约定在 Fill 返回后再将 ctx 用于系统分析或 AI，因此传入 pipeline / AI 的 ctx 或 summary 为本周期完整拉取结果，**不会在拉取中途把不完整信息传出去**。

### 3. 系统如何执行：错峰 + 完整传递给 AI/系统

#### 3.1 执行顺序（保证「完整」）

每个流程（主周期、系统周期、止盈止损调整）内的约定是：

1. **先错峰**：进入该流程后，按 `ctx.Flow` 做一次 `WaitFlowStagger`（系统周期 0s、主周期 20s、止盈止损调整 40s），再开始发 Coinglass 请求。
2. **同步拉齐**：`FillCoinglassData` / `FillCoinglassDataForSLTP` 会**顺序执行**本流程内所有 Coinglass 请求（中间受每分钟请求数限速），**全部执行完才返回**（无论每个请求成功或失败）。
3. **再往下游**：只有 Fill 返回后，才用当前 `ctx` 做 pipeline、生成 prompt、调用 AI。因此传给 AI 和系统的是「本周期已尝试拉取完毕」的完整结果，不会在拉取中途把半成品 ctx 传出去。

主周期：`buildTradingContext("主周期")` 内先设 `ctx.Flow="主周期"`，再 `FillCoinglassData(ctx)`，返回后同一 ctx 用于 pipeline 与 `GetFullDecisionWithStrategy`。  
止盈止损：`BuildLiveMarketSummaryForSLTP` 里 `ctx.Flow="止盈止损调整"`，再 `FillCoinglassDataForSLTP(ctx)`，返回后用 `FormatMarketContextForSLTP(ctx)` 生成 summary 传给 AI。

#### 3.2 数据获取失败时如何传递

- **记录**：每次 Coinglass 调用（成功或失败）都会 `recordCoinglass(ctx, dataType, err, durationMs)`，写入监控模块，在「数据统计」页按机制/数据源/接口展示，包括成功与否和错误信息。
- **ctx 内容**：某次请求失败时，该请求对应的 ctx 字段**不写入**（保持 nil/零值/空），其它已成功的请求照常写入。Fill 仍会继续执行后续请求，不会因单次失败中断整个流程。
- **传给 AI / 系统**：格式化 prompt 或 market summary 时，只对「有值」的字段拼字符串（如 `if ctx.FearGreedValue > 0 || ctx.FearGreedClassification != ""` 才拼 Fear&Greed 行）。因此**失败在语义上被传递为「该项数据缺失」**：AI 和系统看到的是「没有该指标」，而不是「该指标获取失败」的显式句子；如需让 AI 明确知道某类数据缺失，可在 prompt 中另行说明或后续在格式化时增加「XXX 数据暂不可用」的占位。

### 2. `404` / `Not Found`

**现象**：如 `GetLiquidationAggregatedHeatmap` 等接口返回 `{"code":"404","msg":"Not F..."}`。

**原因**：  
接口路径或参数与 Coinglass 当前版本不一致，例如：

- 官方将 `aggregated-heatmap` 改为其他路径（如 `heatmap/model2`）；
- 或必填/可选参数（如 `symbol`、`range`）变更或不再支持。

**建议**：

1. **查官方文档**：对照 [Coinglass API 文档](https://www.coinglass.com/docs) 确认该接口的路径与参数是否已变更。
2. **KeyStore 代理**：若通过 KeyStore 代理访问，确认代理支持的 Coinglass 版本与当前代码中的 path 一致。
3. **代码适配**：若接口已迁移，在 `provider/coinglass/liquidation.go` 中更新路径或参数（如 `aggregated-heatmap` → 新 path），并同步更新调用处（如 `kernel/engine.go` 中的 `GetLiquidationAggregatedHeatmap` 调用）。

---

## 三、其他错误

若错误信息为**解析失败**（如 `parse`、`json`、`unmarshal`），多为响应格式变更或非 JSON；需对照当前 API 响应格式调整 `provider/coinglass` 中的结构体与解析逻辑。

若为**超时**或**网络错误**，请检查本机/服务器到 Coinglass 或 KeyStore 的网络与防火墙，以及 `.env` 中的代理/超时配置。
